Lesson 9: Project, a single-page app from two public APIs, built by an agent

About 30 minutes to read, then about 15 to 18 hours of project work across the module, Module 1 ProjectAgent craft

The project is the GSG week 3 API project, and the difference is that an agent writes the code while you write the spec, set the rules and check the result. Your mentor grades the documents you produce and your review notes, because those show the judgment that employers hire for.

What the GSG brief asks for

The GSG project brief (learning-code/curriculum/coursebook/week-3/project.md) asks for a simple web app, ideally a single page, that queries at least two APIs and uses the results to update the page. You choose what to build, and the brief keeps its requirements short.

The requirements from the brief, which you keep, are these:

  • The app queries at least two APIs and shows dynamic content.
  • The README documents the user journey and the key decisions about how the code is structured.
  • The JavaScript is split into small functions with a clear input and output, and the pure functions have tests. The brief doesn't expect tests on the DOM or on API responses.
  • The design is responsive and mobile-first.
  • Any private API key is kept out of the published code.

The coursebook asks for XMLHttpRequest. Today we write fetch(), which lesson 8 covered, or ky if your decision record chose it.

The brief also lists checks to make before you choose an API. Each check now links to a lesson in this module:

Check from the briefHow you check itLesson
Are there issues with CORS requests?Make one request from a page in the browser, and read the Network tab and the console.Lesson 7
Is the rate limit high enough?Read the API docs, and look for a 429 status or rate limit headers in a response.Lesson 6
Is a free API key available?Read the docs. A key in browser code is public, so prefer APIs that need no key.Lessons 7 and 8
Can you use it without user login (OAuth)?Read the docs. Skip APIs that need each user to log in.Module 4
Is good documentation available?Check that every endpoint you plan to use is in the docs, with an example response.Lesson 4

A static site has no server, so every file you publish, including any API key in it, can be read by anyone who opens the page. The GSG brief notes that a private key rules out GitHub Pages, and Module 2 moves API calls to a server so the key can stay secret. For this project, choose two APIs that need no key, or that issue a key meant for use in browser code.

More examples (optional)

Here are two app ideas that fit the brief with two APIs. The first is a trip planner that shows the weather for a city and a list of nearby sights. The second is a book page that shows a book's details from one API and its author's biography from another.

The public-apis list marks each API with whether it needs a key and whether it supports CORS. Treat those marks as a starting point and check them yourself, because the list can be out of date.

How you and the agent split the work

In lesson 2 you learned to direct a session the way Thorsten Ball describes, where you decide the design and the agent fills in the code. In this project you write three documents before the agent writes any app code, and you keep all three in the repo, as lesson 3 explained.

  1. spec.md holds the user stories, in the form "As a ..., I want ..., so that ...". Each story has acceptance criteria that you can test, e.g., "When the city isn't found, the page shows a message and no error appears in the console".
  2. AGENTS.md holds the rules for every session, e.g., the commands to run the tests and the app, the file layout, "no new dependencies without asking", and "never put an API key in the code".
  3. docs/decisions/0001-http-client.md is the decision record from lesson 8.

Each agent session then handles one user story. You start each session by pointing the agent at spec.md and the story, and you end it with proof and a commit, as lesson 2 described.

More examples (optional)

A starting AGENTS.md for the project could look like this. Change the commands to match your project:

# Weather and sights app

Single-page app, plain HTML, CSS and JavaScript, no framework.
The spec is in spec.md. Decisions are in docs/decisions/.

## Commands
- Run tests: npm test
- Serve locally: npx serve .

## Rules
- Work on one user story per session, and name it in the commit message.
- Put pure functions in src/logic.js and test them in src/logic.test.js.
- Don't add a dependency without asking me first.
- Never put an API key or token in any file.
- Only call endpoints that appear in the API docs linked in spec.md.
- Never weaken or delete a test to make it pass. Tell me instead.

A user story with acceptance criteria could look like this:

## Story 2: Weather for a city
As a traveller, I want to type a city and see today's weather,
so that I can decide what to pack.

Acceptance criteria
- Typing "Gaza" and pressing Enter shows the temperature in °C.
- An unknown city shows "City not found" and no console error.
- The request appears in the Network tab with status 200.

Proof, review and the failures to look for

An agent will say a feature works, but your mentor will only accept evidence that it works. For each user story, save the proof in a proof/ folder or paste it into the pull request.

The proof for each user story comes from three places. First, a screenshot of the Network tab, or the output of curl -v, shows the request and the status code for each API, as you read them in lesson 5. Second, the test output shows that the pure functions pass. Third, a short note says which acceptance criteria you checked by hand in the browser.

When all the stories are done, review the code in a fresh agent session that didn't write it. A fresh session has no memory of the choices it made, so it reads the code as someone else's code.

Run git diff on the whole project against the first commit.
Review it as code someone else wrote, against spec.md and AGENTS.md.
List every problem with the file, the line, and why it's a problem.
Don't fix anything yet.

You then check each finding yourself, write your conclusions in review.md, and only then ask an agent to fix the findings you agree with. The failures below are the ones to look for first in this project:

  • An API key or token appears in a JavaScript file, an HTML file or the git history.
  • A CORS error was "fixed" with a wildcard header or a public proxy that you didn't approve, as lesson 7 described.
  • The code calls an endpoint or a query parameter that isn't in the API's docs.
  • A test was changed so that it can't fail, e.g., expect(result).toBe(3) became expect(result).toBeDefined().
  • The agent added a dependency, retries on a 404, or a fetch() call that never checks response.ok.
More examples (optional)

To search the whole git history for a key, and not only the current files, ask the agent to run the command below and show you the output. Replace YOUR_KEY_PREFIX with the first characters of your key:

git log -p --all | grep -n "YOUR_KEY_PREFIX"   # search every version of every file

A key that was committed and then deleted is still in the history, so deleting the line isn't enough. In that case you revoke the key with the API provider and create a new one.

Do it

The time for each step is an estimate, and the total is about 15 to 18 hours. Commit after every step, so you can review each change and undo it if you need to.

  1. About 2 hours. Create the project repo inside the module folder from lesson 5, and choose two APIs with the checks in the table above.

    mkdir -p ~/code/agents-lab/module-1/api-app   # project folder
cd ~/code/agents-lab/module-1/api-app         # move into it
git init                                      # start the repo
npm init -y                                   # create package.json for tests

    You should now have an empty repo and a short note in spec.md that names both APIs and gives the result of each of the five checks.

  2. About 2 hours. Write the user stories and acceptance criteria in spec.md, including the user journey that the GSG brief asks for. Write them yourself, without the agent.

    You should now have three to five user stories, and every story has acceptance criteria that someone else could check.

  3. About 1 hour. Write AGENTS.md and the decision record from lesson 8.

    You should now see the agent mention your rules when you start a session and ask it "What are the rules for this repo?". If it can't name them, check that no CLAUDE.md file is hiding your AGENTS.md, as lesson 3 explained.

  4. About 8 to 10 hours. Build the app one user story per session. Start each session with a prompt that names the story, the files, the edge cases and the proof you want.

    Read spec.md and AGENTS.md. Implement story 2 only.
Put the pure functions in src/logic.js with tests in src/logic.test.js.
Edge cases: unknown city, empty input, API returns 429.
When you're done, run npm test, and tell me exactly what to click in the browser to check each acceptance criterion.

    You should now have one commit per story, each with passing tests and its proof saved.

  5. About 2 hours. Run the fresh-session review from the section above, write review.md, and fix the findings you agree with in new sessions.

    You should now have a review.md that lists each finding and says whether you fixed it, rejected it, or left it for later, and why.

  6. About 1 hour. Publish the app on GitHub Pages, which hosts the HTML, CSS and JavaScript files from a repository. Push the repo to GitHub first, and confirm that no key is in the code or the history.

    You should now be able to open the app at its github.io address on your phone.

Check yourself

Each item below is a finding from a review. Decide whether it blocks the hand-in, or whether you note it in review.md and move on.

app.js contains the weather API key as a string.

A test changed from toBe(3) to toBeDefined() in the last commit.

The code calls /v2/sights/nearby, and the API docs don't list that path.

Some functions use getCity and others use fetchCityData for similar work.

The README has no user journey.

Hand-in checklist for your mentor

public-apis on GitHub. Use the list to choose your two APIs. For each candidate, read the "Auth" and "CORS" columns, then open the API's own docs to confirm them.
When you finish, tell your teacher (the agent) two things. First, could you follow this project brief alone, on a scale of 1 to 5? Second, where did you get stuck, if anywhere? Your answers go into feedback/module-1.md and are used to improve the brief.
