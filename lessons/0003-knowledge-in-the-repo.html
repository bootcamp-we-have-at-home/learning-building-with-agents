Lesson 3: Keeping project knowledge in the repo and in saved sessions

About 40 minutes, Module 0 Agent craft

Every agent session starts with an empty context, so the only things an agent knows about your project are the things it can read in the repo. A team hiring you will check whether a new teammate, or a new agent session, can pick up your project from the repo alone.

An agent session starts with no knowledge of your project

In lesson 1 you saw that the model only sees what is in its context, i.e., the messages, tool results and files that the loop has added so far. When a session ends, that context is gone, and the next session starts again from nothing.

Some agent tools offer a memory feature, which writes notes that the agent loads in later sessions. For example, Claude Code's docs describe "auto memory" as "notes Claude writes itself based on your corrections and preferences" (Claude Code docs, memory). The course doesn't use memory features, because the notes live outside the repo, so teammates and other tools can't see them, and nobody reviews them in a pull request.

The course uses the repo itself as the memory, so every fact about the project has one home that a person and any agent can read.

Each kind of knowledge has its own place in the repo. The table below shows where each kind belongs:

PlaceWhat it records
The code and its testsWhat the project does, and what must stay true
Commit messagesWhy each change was made
AGENTS.mdHow to work in the repo, e.g., the build and test commands, the conventions and the limits
Saved session transcriptsHow a decision was reached, including what the human asked for and what was rejected
More examples (optional)

A commit message only helps a later session if it says why. The first message below repeats what the diff already shows, and the second one adds a reason that no other place records:

Update auth.js                                   # says nothing the diff doesn't show

Store sessions in Postgres instead of memory     # what changed
                                                 # (blank line)
Sessions were lost on every restart, so users    # why it changed
were logged out after each deploy.

Git history is also useful context for an agent. Thorsten Ball writes that "raw commits contain so much information to inject relevant context into a prompt" (How I Use Amp). For example, you can prompt "Look at commit abc123, which added the products route, and add a categories route in the same way."

Read more: Chris Beams, How to write a Git commit message, and Thorsten Ball, How I Use Amp

AGENTS.md tells every agent how to work in the repo

You already put a README.md in a project for human readers. An AGENTS.md file is the matching file for agents, and the format's site describes it as "a simple, open format for guiding coding agents" (agents.md).

The file is plain Markdown with no required fields or headings. The site suggests a few common sections, e.g., the build and test commands, the code style, testing instructions and security considerations.

Keep the file short, and only write facts that an agent can't work out from the code. The build and test commands are the most useful part, because an agent that knows the test command can run the tests and fix its own errors. Thorsten Ball describes this: "Since what 'the build' is, is documented in the AGENTS.md, the agent will just run the command and then fix the errors" (How I Use Amp).

# Notes app

A command line app that saves notes as Markdown files.

## Commands
- Run the tests: `node --test`
- Run the app: `node notes.js add "My title"`

## Conventions
- Plain JavaScript (ES modules), no TypeScript, no build step.
- Every new function gets a test in `test/`.

## Limits
- Don't add npm dependencies without asking first.
- Run `node --test` before you say a task is finished, and show the output.

Each tool finds AGENTS.md in a slightly different way. The table below was checked against each tool's docs on 2026-10-14.

ToolHow it reads AGENTS.mdSource
Claude CodeReads AGENTS.md in the working directory and the directories above it, from v2.1.277. If a CLAUDE.md, .claude/CLAUDE.md or CLAUDE.local.md exists in any of those directories, Claude Code reads only the CLAUDE.md files and ignores AGENTS.md.docs
CodexReads AGENTS.md from the project root down to the working directory, at most one file per directory, and a file closer to the working directory overrides earlier ones. An AGENTS.override.md takes the place of AGENTS.md in its directory. The combined files are cut off at 32 KiB by default.docs
opencodeSearches upward from the working directory for AGENTS.md or CLAUDE.md, and the first match wins. When both exist in the same place, only AGENTS.md is loaded.docs
piLoads context files (AGENTS.md or CLAUDE.md) from its own agent directory, the working directory and its parent directories. Not verified: which file wins when both exist in one directory.docs
AmpAlways includes AGENTS.md in the working directory and parent directories up to your home folder. It includes an AGENTS.md in a subfolder when the agent reads a file in that subfolder. If a directory has no AGENTS.md, Amp uses AGENT.md or CLAUDE.md instead.docs

The Claude Code rule can catch you out without any warning. For example, a CLAUDE.md that an old tutorial left in ~/code makes Claude Code skip your project's AGENTS.md, while Codex, opencode and Amp still read it. When Claude Code does load the file, it prints a line such as AGENTS.md loaded: /home/you/repo/AGENTS.md at the start of the session, so look for that line.

More examples (optional)

A repo with several packages can have one AGENTS.md per package. The agents.md site says "the closest AGENTS.md to the edited file wins", so the package file can override the root file for that package:

AGENTS.md              # shared rules, e.g., the commit message style
server/AGENTS.md       # server rules, e.g., "run npm test in server/"
client/AGENTS.md       # client rules, e.g., "run npm run lint in client/"

Facts that the code already shows don't belong in AGENTS.md. For example, "the project uses Express" is visible in package.json, so writing it again only adds tokens that the agent reads in every session.

Read more: agents.md, and Birgitta Böckeler, Context Engineering for Coding Agents

Saved sessions record how a decision was made

A commit message says why a change was made, but it leaves out the discussion that led there, e.g., the options you rejected and the questions you asked. The transcript of the session holds that discussion.

The Amp team builds on that idea. Quinn Slack says that "all of our intent, all of our history is in Amp, in threads, in something that is legible to the agent" (Raising an Agent, season 2, episode 4). Amp's agent can read an old thread when it needs a detail, and the team writes that it "goes back and looks instead of trusting the compaction" (Read Bigger Threads).

Compaction is when a tool replaces older messages with a short summary to free up context. Amp removed compaction in 2025 and then brought it back in May 2026 (Amp, Rebuilt), but in both versions the full thread stays available to re-read, and a summary can lose details that the full transcript keeps.

You can follow the same practice in any tool, in four steps:

  1. First, at the end of a session, save the transcript into the repo, e.g., docs/sessions/2026-10-14-slugify.md.
  2. Second, add a Session: line at the end of the commit message that points to the saved file. Amp adds a similar Amp-Thread-ID line to its commits (Amp threads docs).
  3. Third, before you stop a long piece of work, ask the agent for a handoff note with the goal, the decisions made, the relevant files and the open questions, and edit it yourself.
  4. Fourth, in a later session, point the agent at the source, e.g., "Read docs/sessions/2026-10-14-slugify.md and list what we decided about accented letters."

Read a transcript before you commit it, because it can contain secrets. The pi docs warn that a session "can contain prompts, tool output, file contents, and credentials exposed during the conversation" (pi usage docs).

More examples (optional)

A handoff note is short, and you edit it before you trust it. Here is an example:

# Handoff: slugify for note file names

Goal: note titles become safe file names.
Decided: lowercase, spaces become hyphens, other symbols are removed.
Files: slugify.js, test/slugify.test.js
Open question: should accented letters (é) become plain letters (e) or be removed?

A new session can start from the note with the prompt "Read docs/handoff.md, then answer the open question by checking what the tests expect." The new session has a small, focused context, and it doesn't carry the failed attempts from the old session.

Read more: Amp, Handoff, and git docs on commit trailers

Do it

  1. Create a practice repo for Module 0.

    mkdir -p ~/code/agents-lab/module-0/notes-app   # create the folder and its parents
cd ~/code/agents-lab/module-0/notes-app         # move into it
git init                                        # start a git repo here

    You should now see Initialized empty Git repository in and the path of your new folder.

  2. Create AGENTS.md in the repo, with the example content from the AGENTS.md section above, using your editor.

    cat AGENTS.md   # print the file to check it

    You should now see the file's headings, Commands, Conventions and Limits.

  3. Check that no CLAUDE.md file in this folder or above it would hide your AGENTS.md from Claude Code. The loop below checks each parent folder in turn.

    d=$PWD; while [ "$d" != / ]; do ls "$d"/CLAUDE.md "$d"/CLAUDE.local.md "$d"/.claude/CLAUDE.md 2>/dev/null; d=$(dirname "$d"); done   # list any CLAUDE files up the tree

    You should now see no output, which means nothing hides AGENTS.md. If a path appears, Claude Code reads that file instead, so ask your mentor before you move or delete it.

  4. Start your agent in the repo, and give it this prompt:

    Without opening any files, tell me the test command for this project
and the name of the file you learned it from.

    You should now see the agent answer node --test and name AGENTS.md. In Claude Code, you should also see the AGENTS.md loaded line at the start of the session.

  5. Give the agent a small task that follows the rules in AGENTS.md:

    Add slugify.js, which turns a note title into a safe file name:
lowercase, spaces become hyphens, other symbols are removed.
Add a test in test/slugify.test.js. Run the tests and show me the output.

    You should now see the test output with pass and fail 0 in the agent's reply. Run node --test yourself to confirm.

  6. Save the session transcript into the repo with your tool's command from the table above, as docs/sessions/ plus today's date and -slugify.md. Then read the file and remove anything secret.

    ls docs/sessions/   # check that the transcript file exists

    You should now see one file with today's date in its name.

  7. Commit the work with a message that says why, and add a Session: line. Each -m becomes one paragraph of the message, and you should change the file name to match your transcript.

    git add .
git commit -m "Add slugify for note file names" -m "Note titles can contain spaces and symbols that break file paths, so the app turns each title into lowercase words joined by hyphens." -m "Session: docs/sessions/2026-10-14-slugify.md"
git log -1 --format='%(trailers)'   # print only the trailer lines of the last commit

    You should now see Session: docs/sessions/2026-10-14-slugify.md, with your own file name.

  8. Exit the agent, start a new session in the same folder, and give it this prompt:

    Using only the repo (code, git log and docs/sessions), explain why
slugify.js exists and what rules it follows. Quote your sources.

    You should now see the agent quote the commit message and the saved transcript, even though the new session started with an empty context.

Check yourself

Decide where each piece of knowledge belongs. Answer from memory before you scroll up.

"Run the tests with npm test, and run them before you say a task is finished."

"We switched from bcrypt to argon2 because the server image has no compiler for native modules."

"Goal: the login form. Done: validation. Open: should the error say whether the email exists?"

"The regex removes the byte order mark, because the bank's CSV export adds one."

"The agent was confused about the folder layout for a while, and then it worked it out."

"Never edit a migration file that has already run. Add a new migration instead."

"The database password is hunter2."
