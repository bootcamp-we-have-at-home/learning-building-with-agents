Lesson 7: Why the browser blocks some requests, with same-origin and CORS

About 40 minutes, Module 1 Systems modelAgent craft

The GSG week 3 project brief tells you to check "Are there issues with CORS requests?" before you choose an API, because a CORS error can block a front-end-only app completely. Agents often respond to a CORS error with a header or a workaround that removes the error and also removes a protection, so you need to know which fix is correct.

An origin is the scheme, host and port of a page

In lesson 5, the URL https://example.com had a scheme (https), a host (example.com) and a port (443). The browser combines the three parts into the page's origin, and MDN defines it this way: "Two URLs have the same origin if the protocol, port (if specified), and host are the same for both" (MDN, same-origin policy).

For example, a page at http://localhost:5500 and an API at http://localhost:5600 have different origins, because the ports differ. In your projects, the front end and the API often run on different ports during development, so they are cross-origin even though both run on your laptop.

The same-origin policy is a rule that the browser enforces. It stops JavaScript on one origin from reading a response that came from another origin, unless the other server says the read is allowed.

The browser usually sends the request and blocks only the reading of the response, so the server receives the request and answers it.

The following output shows the rule in action. It was captured on 2026-10-14 with two small Node servers and Chromium 151. A page on port 5500 called fetch("http://localhost:5600/api/products"), and the API server on port 5600 sent no CORS headers. The API server's own log shows that it received the request:

GET /api/products Origin: http://localhost:5500

The API answered with status 200 and the product list. The browser then refused to give the response to the page's JavaScript, and it printed this message in the console:

Access to fetch at 'http://localhost:5600/api/products' from origin 'http://localhost:5500'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the
requested resource.

CORS, which stands for Cross-Origin Resource Sharing, is the way a server tells the browser which other origins may read its responses. The main header is Access-Control-Allow-Origin, and its value is either one exact origin, e.g., http://localhost:5500, or * for any origin (MDN, CORS).

More examples (optional)

MDN compares the URL http://store.company.com/dir/page.html with other URLs. The comparisons below come from the MDN page:

URLSame origin?Reason
http://store.company.com/dir2/other.htmlYesOnly the path differs.
https://store.company.com/page.htmlNoThe scheme differs.
http://store.company.com:81/dir/page.htmlNoThe port differs, because http:// uses port 80 by default.
http://news.company.com/dir/page.htmlNoThe host differs.

You saw CORS headers on real APIs in lesson 6 without noticing them. The GitHub API and httpbin.org both sent access-control-allow-origin: * on 2026-10-14, so any web page can read their public responses from JavaScript.

Simple requests and preflighted requests

The GET request in the previous section went straight to the server, but some requests need the browser to ask for permission first. MDN calls the requests that go straight through "simple requests", and a simple request must meet all of its conditions. The method must be GET, HEAD or POST, and the Content-Type can only be application/x-www-form-urlencoded, multipart/form-data or text/plain, among other conditions (MDN, CORS).

For any other request, the browser first sends a preflight request with the OPTIONS method. The preflight carries headers such as Access-Control-Request-Method, and the browser sends the real request only if the server's answer allows it.

A POST that sends JSON is not a simple request, because application/json is not on the list of allowed content types. When the same test page sent a JSON POST to an API without CORS headers, the API's log showed only the preflight, and the POST itself was never sent:

OPTIONS /api/cart Origin: http://localhost:5500

The console message then named the preflight as the failing step:

Access to fetch at 'http://localhost:5600/api/cart' from origin 'http://localhost:5500'
has been blocked by CORS policy: Response to preflight request doesn't pass access control
check: No 'Access-Control-Allow-Origin' header is present on the requested resource.

The page's JavaScript gets almost no detail about a CORS failure. MDN says that "specifics about the error are not available to JavaScript", and in the test above the fetch() promise rejected with only TypeError: Failed to fetch. The full reason is only in the browser's console and Network tab, so an agent that reads only the JavaScript error is guessing.

More examples (optional)

A request that sends a custom header, e.g., Authorization: Bearer ..., also needs a preflight, because Authorization is not one of the headers that a simple request may set. Most requests to a private API carry that header, so most of them are preflighted.

When the test API was changed to answer with Access-Control-Allow-Origin: http://localhost:5500, Access-Control-Allow-Methods: GET, POST and Access-Control-Allow-Headers: Content-Type, the log showed both requests, the preflight and then the real one:

OPTIONS /api/cart Origin: http://localhost:5500
POST /api/cart Origin: http://localhost:5500

Judging the agent's CORS fix

CORS controls what JavaScript in a browser may read, and it doesn't stop anyone from calling the server. The curl command below asked the same test API for the products on 2026-10-14, while the API still sent no CORS headers, and the API returned the data:

$ curl -s -i http://localhost:5600/api/products
HTTP/1.1 200 OK
Content-Type: application/json

[{"id":1,"name":"mug"}]

Curl doesn't apply the same-origin policy, and neither do scripts or other servers. CORS is not access control for your API, so a private API still needs authentication, which Module 4 covers.

The fix an agent reaches for most often is Access-Control-Allow-Origin: *, and the wildcard is correct in one case. It is fine for public data that anyone may read and that needs no cookies, e.g., the GitHub API's public repository data.

The wildcard is wrong when the browser sends credentials such as cookies. MDN says the server "must not specify the * wildcard" for a credentialed request, and the browser blocks the response. The test page sent a request with credentials: "include" to an API that answered with *, and Chromium printed this message:

Access to fetch at 'http://localhost:5600/api/products' from origin 'http://localhost:5500'
has been blocked by CORS policy: The value of the 'Access-Control-Allow-Origin' header in the
response must not be the wildcard '*' when the request's credentials mode is 'include'.

For your own API, the correct fix is to name the exact origin of your front end, and to add Access-Control-Allow-Credentials: true only when the front end sends cookies.

A different problem is a third-party API that sends no CORS headers at all. You can't change another company's server, so no change in your front-end code can make the browser accept the response. The fix is to call the API from your own server and to have your page call your server, which Module 2 builds. Agents sometimes suggest a public "CORS proxy" service instead, but the proxy service then sees every request and response, including any API key that you send through it.

The same reasoning applies to API keys. Any key that your front-end JavaScript sends is visible to every visitor in the Network tab, so the GSG brief's question "Is a free API key available?" leads to a second question, which is whether the key must stay secret. A key that must stay secret belongs on a server.

More examples (optional)

An agent that can't fix a CORS error sometimes suggests launching Chrome with web security turned off. The page then works on your machine and fails for every user, because the users' browsers still enforce the same-origin policy. Treat any fix that changes your browser rather than the server's headers as hiding the error.

Another example is an agent that adds the CORS header to the page server instead of the API server. The header has to come from the server whose response is being read, i.e., the API on port 5600 in the test above, so adding it to the page server on port 5500 changes nothing.

Do it

  1. Create a folder for this lab inside your module folder from lesson 5.

    mkdir -p ~/code/agents-lab/module-1/cors   # a new folder for this lab
cd ~/code/agents-lab/module-1/cors         # move into it

    You should now see the new path when you run pwd.

  2. Open your coding agent in the folder, and give it this prompt. The prompt asks for no CORS headers on purpose.

    Create two Node servers using only the built-in http module, with no npm packages.
1. page-server.js listens on port 5500 and serves one HTML page. The page calls
   fetch("http://localhost:5600/api/products") and shows the JSON on the page,
   or shows "fetch failed: " plus the error message if the fetch rejects.
2. api-server.js listens on port 5600. For every request it logs the method, the URL
   and the Origin header, then answers 200 with [{"id":1,"name":"mug"}] as JSON.
Do not add any CORS headers. Do not start the servers; I will run them myself.

    You should now see the files page-server.js and api-server.js in the folder. Read both files before you run them, and check that neither one sets an Access-Control header.

  3. Start each server in its own terminal window, from the same folder.

    node api-server.js    # terminal 1, leave it running
node page-server.js   # terminal 2, leave it running

    You should now see each server print that it is listening, and both terminals stay busy. You stop a server later with Ctrl+C.

  4. Open http://localhost:5500 in Chrome or Firefox, press F12 to open the developer tools, and select the Console tab. Reload the page once with the tools open.

    You should now see "fetch failed" on the page and a CORS message in the console that says no Access-Control-Allow-Origin header is present. Terminal 1 should show a GET /api/products line, which proves the request reached the server.

  5. Select the Network tab in the developer tools, reload the page, and select the request to localhost:5600 in the list.

    You should now see that the browser marks the request as failed because of CORS, even though terminal 1 shows that the server answered it.

  6. Run curl against the API in a third terminal, to see that CORS doesn't apply outside the browser.

    curl -i http://localhost:5600/api/products   # no browser, so no same-origin policy

    You should now see HTTP/1.1 200 OK and the product list, with no error.

  7. Give your agent this prompt, and then judge its fix with the questions under the prompt.

    The page on port 5500 can't read the response from the API on port 5600 because of CORS.
Fix it. Tell me which file you changed and which header you added, and why.
Then show me curl -i output from the API that proves the header is there.

    You should now see a change to api-server.js and curl output with an Access-Control-Allow-Origin header. Before you accept the change, check three things. The header must be on the API server, the value should be http://localhost:5500 rather than *, and the agent must not have suggested changing browser settings. Restart terminal 1 with Ctrl+C and node api-server.js, reload the page, and confirm that the product list appears. Stop both servers with Ctrl+C when you finish.
