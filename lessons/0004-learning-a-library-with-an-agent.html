Lesson 4: Learning a new library with an agent, from its docs and source

About 40 minutes, Module 0 Agent craftBuild, then buy

Agents write code for the version of a library they saw in training, so they make confident mistakes with libraries that are new or have changed since then. You need to understand a library well enough to catch those mistakes, and an agent can teach you that quickly if you point it at the right sources.

A model knows a library as it was when its training data ended

In lesson 1 you saw that the model works from two things, the text in its context and what it learned in training. The training data stops at a date called the training cutoff, and the model knows nothing that happened after it.

Libraries keep changing after that date. When the agent writes code for a library that has changed, it writes the old API with the same confidence as a correct one, and nothing in its answer warns you.

The library ky is a real example. Ky is a small wrapper around fetch, and you'll decide between ky and plain fetch in lesson 8. In ky version 1, the option for a base address was called prefixUrl. Version 2.0.0, released on 2026-04-06, renamed it to prefix and added a new baseUrl option (ky v2.0.0 release).

An agent trained mostly on ky 1 code will write prefixUrl. With ky 2.2.0 installed, the result is the error below, captured on 2026-10-14:

The `prefixUrl` option has been renamed `prefix` in v2 and enhanced to allow slashes in input.
See also the new `baseUrl` option for improved flexibility with standard URL resolution:
https://github.com/sindresorhus/ky#baseurl

Ky's authors wrote a helpful error for the old name, but many libraries ignore an option they don't know. In that case the code runs without an error and does the wrong thing, and only a test or a careful reader notices.

More examples (optional)

The npm registry shows the dates of each ky release. The output below was captured on 2026-10-14 with npm view ky time --json and shortened:

"1.14.3": "2026-01-25T17:30:20.212Z",   # last version 1 release
"2.0.0":  "2026-04-06T08:00:06.813Z",   # the release that renamed prefixUrl
"2.2.0":  "2026-10-09T06:32:47.556Z"    # the current version

An agent can also invent a method that never existed. For example, an answer that uses ky.fetchJson(url) looks plausible, but no ky version has that method. The installed type definitions, node_modules/ky/distribution/index.d.ts, list every method, so a search there settles the question in a few seconds.

Read more: ky release notes

Point the agent at the version you have installed

When you ask the agent about a library, tell it which sources to read before it answers. The best sources describe the exact version in your project, and each source below is closer to the installed code than the one after it.

  1. First, package.json and npm ls ky tell you which version is installed.
  2. Second, the files inside node_modules/ky/ match that version exactly. Ky ships its readme.md and its type definitions in distribution/index.d.ts.
  3. Third, the release notes explain what changed between the version the agent remembers and the version you have.
  4. Fourth, the official docs site describes the latest version. Some sites also publish an llms.txt file, a Markdown index of the docs written for language models (llmstxt.org). For example, the Claude Code docs publish one at https://code.claude.com/docs/llms.txt.

Ask the agent to quote the lines it relies on, because a quote is something you can check in a few seconds, while a summary isn't.

We use ky, and the installed version is in package.json.
Before you answer, read node_modules/ky/readme.md and
node_modules/ky/distribution/index.d.ts.
Quote the lines you rely on, with the file name for each quote.
More examples (optional)

A grounded answer quotes the installed readme. For example, ky 2.2.0's readme lists the default retry settings, and the two lines below show that ky retries a failed request 2 times and that post isn't in the list of retried methods:

- `limit`: `2`
- `methods`: `get` `put` `head` `delete` `options` `trace` `query`

Those two lines answer a design question for your project. A failed POST that creates an order won't be sent twice by ky's default settings, so the order won't be created twice.

Read more: llmstxt.org, and Birgitta Böckeler, Context Engineering for Coding Agents

Test your understanding in a spike, and write down what you learn

Reading the docs tells you what the library should do, and running it tells you what it does. A spike is a small throwaway program that answers one question, and you keep it in a separate folder so it never ends up in the project.

Write down your prediction before you run the spike. Where your prediction and the output differ, your understanding of the library was wrong, and you have found the exact thing to learn.

The spike below asks three questions about ky 2.2.0, and an agent wrote it after reading the installed readme:

import ky from 'ky';

const api = ky.create({ baseUrl: 'https://httpbin.org/' });

// 1. A JSON GET
const data = await api.get('json').json();
console.log('1. title:', data.slideshow.title);

// 2. A 404: ky throws, fetch would not
try {
  await api.get('status/404');
} catch (error) {
  console.log('2.', error.name, error.response.status);
}

// 3. The v1 option name
try {
  await ky.get('json', { prefixUrl: 'https://httpbin.org/' });
} catch (error) {
  console.log('3.', error.message);
}

Running node spike.mjs on 2026-10-14 with Node 26 printed the following. The third line is shortened:

1. title: Sample Slide Show
2. HTTPError 404
3. The `prefixUrl` option has been renamed `prefix` in v2 and enhanced to allow slashes in input. ...

The second result shows a difference from plain fetch, which doesn't throw on a 404. The same request with fetch printed fetch ok: false 404, so with fetch your code has to check response.ok itself.

After the spike, write what you learned into the project repo, e.g., docs/notes/ky.md. Lesson 3 showed that the repo is where later sessions look, so a later agent reads your note with the version and the sources, and it doesn't fall back on its training data.

The aim is to know enough to steer. You don't need to know all of ky, but you need to answer the questions that decide your design, e.g., whether it throws on errors, whether it retries, and which version you have.

More examples (optional)

A note in the repo can be short. Here is an example of docs/notes/ky.md:

# ky (installed: 2.2.0, checked 2026-10-14)

- Throws HTTPError for any status outside 200 to 299 (readme, "Returns a Response").
- Retries 2 times by default, and never retries POST (readme, "retry").
- Base address option is baseUrl or prefix. prefixUrl was the v1 name and now throws.
- Sources: node_modules/ky/readme.md, the v2.0.0 release notes.

Read more: ky readme, the baseUrl section

Do it

  1. Create a spike folder outside your project, and install ky in it.

    mkdir -p ~/code/agents-lab/module-0/ky-spike   # a throwaway folder for the spike
cd ~/code/agents-lab/module-0/ky-spike         # move into it
npm init -y                                    # create a package.json
npm install ky                                 # install the latest ky

    You should now see added 1 package in the output of the last command.

  2. Check which version you installed.

    npm ls ky   # print the installed version

    You should now see ky@2.2.0 or a later version.

  3. Start your agent in the spike folder, and give it this prompt:

    Read node_modules/ky/readme.md and node_modules/ky/distribution/index.d.ts.
Then write spike.mjs that answers three questions about this ky version:
1. How do I GET JSON from https://httpbin.org/json with a base URL option?
2. What happens on a 404 from https://httpbin.org/status/404?
3. What happens if I pass the option prefixUrl?
Quote the readme lines you relied on. Don't run the script.

    You should now see a spike.mjs file and quotes from the readme in the agent's reply.

  4. Before you run anything, write your three predictions in a file named predictions.txt, one line per question.

    You should now have a file with three lines, written by you and not by the agent.

  5. Run the spike.

    node spike.mjs   # run the agent's spike

    You should now see three numbered lines similar to the captured output above. Compare each line with your prediction, and mark each one right or wrong.

  6. Move to the notes-app repo from lesson 3, and ask the agent to record what you learned:

    Write docs/notes/ky.md with what we learned about ky in
~/code/agents-lab/module-0/ky-spike: the installed version, today's date,
the answers to the three questions, and the source of each answer.

    You should now see docs/notes/ky.md in the notes-app repo, and it names the version you installed.

Check yourself

Each statement below comes from an agent's answer about ky, with ky 2.2.0 installed. Decide whether the answer is grounded in the installed version or is invented or outdated.

const api = ky.create({ prefixUrl: 'https://api.example.com' });

"From node_modules/ky/readme.md: ky retries with limit: 2 by default, and post isn't in the retried methods."

const user = await ky.fetchJson('https://api.example.com/user');

"Ky throws an HTTPError on a 404. The spike printed HTTPError 404."

"Ky works the same in every version, so there's no need to check the docs."

The ky readme on GitHub. Read the sections on baseUrl, retry and HTTPError, and compare them with the copy in your node_modules. Then read the v2.0.0 release notes to see everything that changed between ky 1 and ky 2.
When you finish, tell your teacher (the agent) two things. First, could you follow this lesson alone, on a scale of 1 to 5? Second, where did you get stuck, if anywhere? Your answers go into feedback/module-0.md and are used to improve the lesson.
