Lesson 1: An agent is a model, a set of tools and a loop

About 30 minutes, Module 0 Agent craft

Most habits in this course, e.g., starting fresh sessions and asking for proof, follow from how the agent loop works. When you know what the model can see and what it can't, you can predict when an agent will go wrong and steer it before it does.

The model only sees the text that the program sends it

You have used a chat assistant, where you type a message and get an answer back. The part that writes the answer is a language model, which is a program that takes text in and produces text out.

A model can't open your files, run commands or look anything up by itself. It only reads the text it receives on each request, and that text is called the context window.

The model also keeps nothing between requests. Thorsten Ball explains in How to Build an Agent that the provider's server "is stateless", so "we send the whole conversation every time".

Anything that isn't in the context window doesn't exist for the model.

More examples (optional)

A coding agent CLI such as Claude Code or Codex sends more than your message on each request. A typical request contains these parts:

  • a system prompt from the tool's makers, with general instructions
  • a list of the tools the model may ask for, with a description of each
  • the contents of your project's AGENTS.md file, if the project has one (lesson 3 covers AGENTS.md)
  • every message, tool call and tool result in the session so far

If you tell the agent a fact in one session and then start a new session, the new context doesn't contain the fact. The agent only learns it again if the fact is written somewhere the agent reads, e.g., in a file in the repo.

Read more: Anthropic, Effective context engineering for AI agents

Tools and a loop turn a model into an agent

A model that only produces text can describe a change, but it can't make one. Thorsten Ball defines an agent as "an LLM with access to tools, giving it the ability to modify something outside the context window", and Anthropic describes agents as "LLMs using tools based on environmental feedback in a loop" (Building Effective Agents).

A tool call is a request that the model writes in its reply, e.g., "run the command npm test". The model only writes the request, and the program around the model does the work.

The loop works like this:

  1. First, the program sends the whole context to the model.
  2. Second, the model replies with text, with a tool call, or with both.
  3. Third, if the reply contains a tool call, the program runs the tool and adds the tool result to the context. Then it goes back to the first step.
  4. Fourth, if the reply has no tool call, the loop ends and you see the answer.

The coding CLI you use, e.g., Claude Code, Codex, opencode, pi or Amp, is the program that runs the loop. Its tools let the model read files, edit files and run shell commands. Many agent programs also stop after a maximum number of turns, which Anthropic calls a stopping condition.

More examples (optional)

Thorsten Ball's post uses a weather example. When the user asks about the weather in Munich, the model replies with a tool call similar to get_weather(Munich). In his words, the program then does the rest: "We execute the tool, send the result back up to Claude, and ask again for Claude's response."

The model in the session above asked for ls scripts, which failed. A model only knows what earlier tool results showed it, so it sometimes asks for things that don't exist. The error goes back into the context as a tool result, and the model adjusts on the next request.

Read more: Thorsten Ball, How to Build an Agent and Anthropic, Building Effective Agents

Why a fresh and small context gives better results

In the session above, every tool result stayed in the context, and the program sent all of it again on the next request. In a long session, the context fills up with old file contents, failed attempts and earlier tasks.

A longer context makes the model worse at using what is in it. Anthropic's engineers describe research on "context rot", which shows that "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases" (Effective context engineering).

Mixing tasks makes the problem worse. The Amp documentation says "a thread that mixes unrelated work gives the agent a worse context to reason with", so it recommends one thread, i.e., one session, per task (Amp threads).

For you, the practical result is a habit, which is to start a new session for each task and give it only the files and facts that the task needs. Lesson 2 turns the habit into a routine.

More examples (optional)

Suppose you spend a session fixing a bug in the cart, and then you ask the same session to write a README. The context still holds the cart code, the failed fixes and the test output, so the model may describe the old broken behaviour in the README. A new session would see only the code as it is now.

Suppose instead that the agent read a 3,000 line log file early in a session. Every later request sends the full log again, even if the task moved on. You can start a new session and point it at the one part of the log that matters, e.g., "read lines 200 to 240 of server.log".

Do it

  1. Create a practice folder for Module 0, with a tiny project in it. Copy the whole block into your terminal.

    mkdir -p ~/code/agents-lab/module-0/tiny-shop   # create the folder, including parent folders
cd ~/code/agents-lab/module-0/tiny-shop         # move into it
cat > package.json <<'EOF'
{
  "name": "tiny-shop",
  "version": "1.0.0",
  "scripts": { "test": "node --test" }
}
EOF
cat > cart.js <<'EOF'
function total(items) {
  return items.reduce((sum, item) => sum + item.price * item.qty, 0);
}
module.exports = { total };
EOF
cat > cart.test.js <<'EOF'
const test = require("node:test");
const assert = require("node:assert");
const { total } = require("./cart");
test("total adds price times quantity", () => {
  assert.strictEqual(total([{ price: 2, qty: 3 }, { price: 5, qty: 1 }]), 11);
});
EOF
ls                                              # list the files you created

    You should now see cart.js, cart.test.js and package.json. Lesson 2 uses the same project.

  2. Start your coding agent in the tiny-shop folder, and give it this read-only task:

    What does the test script in this project run, and do the tests pass?
Answer in two sentences. Don't change any files.

    You should now see the agent run one or more commands, e.g., reading package.json and running npm test, and then give a two-sentence answer.

  3. Scroll back through the session and write down each item in order, labelled as your message, a tool call, a tool result or model text. Most CLIs show tool calls with the tool's name, e.g., Bash or Read, and show the output underneath.

    You should now have a list that starts with your message and ends with model text that has no tool call after it.

  4. Count the model replies in your list, i.e., the tool calls and the final text. Each reply means that the program sent the whole context to the model one more time.

    You should now have a number, e.g., 3 for the session above, and you can see how much text the last request carried.

  5. Optional, and only if you have an API key and are happy to pay a few cents: ask an agent to build the toy agent from Thorsten Ball's post, in JavaScript. You read and direct, and the agent writes the code.

    Read https://ampcode.com/how-to-build-an-agent and build the same agent in Node,
in a new folder called toy-agent, with only the read_file and list_files tools.
Read the API key from the ANTHROPIC_API_KEY environment variable and never write it to a file.
When it works, show me one session where it calls a tool.

    You should now see a small program that prints the model's tool calls and results as it runs, which is the same loop you labelled in step 3.
