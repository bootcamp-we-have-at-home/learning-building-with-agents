Lesson 6: HTTP methods, status codes and headers

About 30 minutes, Module 1 Systems modelAgent craft

Every API your agent calls or writes speaks in methods, status codes and headers, so you need to read them quickly to judge whether the agent's code tells the truth about what happened. You'll also learn to spot two mistakes that agents make often, which are retries on requests that are unsafe to repeat and errors reported with a success status.

The method says what the client wants the server to do

In lesson 5, curl sent the line GET / HTTP/2, and the word GET in that line is the method. The method tells the server what kind of action the client is asking for, and the path after it says which resource the action applies to.

HTTP defines a small set of methods, and most APIs use the five in the table below. The "safe" and "idempotent" columns come from RFC 9110, section 9.2, and the PATCH row comes from RFC 5789.

MethodUsual meaningSafeIdempotent
GETRead a resource, e.g., GET /products/7YesYes
POSTCreate something or submit data, e.g., POST /ordersNoNo
PUTReplace a resource with the body you sendNoYes
PATCHChange part of a resourceNoNo
DELETERemove a resourceNoYes

A method is safe when the client asks only to read and expects no change on the server. A method is idempotent when sending the same request twice has the same intended effect as sending it once. For example, deleting product 7 twice still leaves product 7 deleted, but posting the same order twice creates two orders.

The difference decides whether an automatic retry is harmless. RFC 9110 says a client can retry an idempotent request after a dropped connection, and it says a client "SHOULD NOT automatically retry a request with a non-idempotent method" unless it knows the request is safe to repeat. When an agent wraps a POST /orders call in automatic retries, a slow network can turn one customer order into two.

More examples (optional)

The httpbin.org test service echoes back whatever you send. The following output was captured on 2026-10-14 with a POST that sent a JSON body. Some header lines are removed:

$ curl -i -X POST https://httpbin.org/post -H 'Content-Type: application/json' -d '{"name":"mug","price":12}'
HTTP/2 200
content-type: application/json

{
  "data": "{\"name\":\"mug\",\"price\":12}",
  "json": {
    "name": "mug",
    "price": 12
  },
  "url": "https://httpbin.org/post"
}

In the output above, the request's Content-Type: application/json header told the server how to read the body, so httpbin parsed the body and returned it under "json".

A server can also refuse a method. When curl sent DELETE to httpbin's /get path on the same day, the server answered with HTTP/2 405 and the header allow: OPTIONS, GET, HEAD, which lists the methods the path accepts.

The status code says how the request went

The response in lesson 5 started with HTTP/2 200, and the number 200 is the status code. The first digit puts every status code in one of five classes, as defined in RFC 9110, section 15:

ClassMeaning in RFC 9110What to do next
1xxInformational: the request was received and processing continuesYou rarely see these in curl or in app code.
2xxSuccessful: the request was received, understood and acceptedUse the response.
3xxRedirection: the client must take a further actionFollow the Location header.
4xxClient error: the request has bad syntax or can't be fulfilledChange the request, because sending it again unchanged gets the same answer.
5xxServer error: the server failed to fulfil a valid requestLook at the server. A retry may work if the failure was temporary.

The codes in the next table cover most of what you'll see in your projects. The full list is on MDN's status code reference.

CodeNameTypical cause
200OKThe request worked, and the body has the result.
201CreatedA POST created a new resource.
204No ContentThe request worked, and there is no body, e.g., after a DELETE.
301Moved PermanentlyThe resource lives at the URL in the Location header.
400Bad RequestThe body or parameters are malformed or missing a field.
401UnauthorizedThe request has no valid credentials, e.g., a missing token.
403ForbiddenThe credentials are valid, but they don't allow this action.
404Not FoundNothing exists at this path.
405Method Not AllowedThe path exists, but it doesn't accept this method.
429Too Many RequestsYou hit a rate limit, so wait before you try again.
500Internal Server ErrorThe server's code failed, e.g., it threw an uncaught exception.
503Service UnavailableThe server is overloaded or down for maintenance.

Most APIs also put an explanation in the body of an error response. The following output was captured on 2026-10-14 from the GitHub API, for a repository that doesn't exist. Some header lines are removed:

$ curl -i https://api.github.com/repos/no-such-owner-zz9/nothing
HTTP/2 404
content-type: application/json; charset=utf-8
x-ratelimit-limit: 60
x-ratelimit-remaining: 59

{
  "message": "Not Found",
  "documentation_url": "https://docs.github.com/rest/repos/repos#get-a-repository",
  "status": "404"
}

In the output above, the status line and the body agree that the repository wasn't found, and the body links to the documentation for the endpoint. Agreement between the status line and the body is what you want to see in any API, including the ones your agent writes.

More examples (optional)

The GitHub API answered 401 on 2026-10-14 when curl asked for the current user without a token. The body says what is missing:

$ curl -i https://api.github.com/user
HTTP/2 401
content-type: application/json; charset=utf-8

{
  "message": "Requires authentication",
  "documentation_url": "https://docs.github.com/rest",
  "status": "401"
}

A redirect looks different, because the important part is a header and the body is empty. The following output is from curl -I http://github.com on the same day:

HTTP/1.1 301 Moved Permanently
Content-Length: 0
Location: https://github.com/

In the output above, GitHub tells the client to use the https:// address instead. Browsers follow the redirect on their own, but curl only follows it if you add the -L flag.

Headers describe the body and the request

You saw header lines in lesson 5, e.g., content-type: text/html. Headers are name and value pairs that travel before the body, and they carry information about the body, the client and the rules for caching. Header names are not case sensitive, so Content-Type and content-type are the same header.

A few headers come up in almost every project, and the table below lists them with real values from the captures in this lesson. The full list is on MDN's header reference.

HeaderSent byWhat it saysReal example
Content-TypeBothThe format of the bodyapplication/json; charset=utf-8
AuthorizationClientThe credentials for the request, e.g., an API tokenBearer <token>
Cache-ControlServerHow long a client or proxy may reuse the responsepublic, max-age=60, s-maxage=60 from the GitHub API
LocationServerWhere a redirected or newly created resource liveshttps://github.com/
Set-CookieServerA cookie for the browser to store and send back. Module 4 covers cookies.Not shown here

APIs also add their own headers. For example, GitHub sends x-ratelimit-limit: 60 and x-ratelimit-remaining: 59 to anonymous clients, so you can see how many requests you have left in the current hour before you get a 403 or 429 (GitHub, rate limits for the REST API).

An agent sometimes writes a server that always answers 200 and puts the error inside the body, e.g., {"error": "Product not found"}. The status line then says the request succeeded while the body says it failed, so every client, cache and monitoring tool that reads the status line gets the wrong answer.

The mistake also hides errors in the browser. The fetch() function only rejects its promise on a network failure, and for any status it resolves and sets response.ok to true for codes 200 to 299 (MDN, fetch). Front-end code that checks response.ok therefore treats a 200 with an error body as a success.

// What the agent wrote: the status line says success
res.status(200).json({ error: "Product not found" });

// What you ask for instead: the status line and the body agree
res.status(404).json({ error: "Product not found" });
More examples (optional)

The same Content-Type header can change how a server reads a request. When you send JSON without Content-Type: application/json, many servers, including Express with its express.json() parser, skip the body, so your handler finds req.body empty or undefined. An agent that "fixes" the empty body by parsing the raw text by hand is working around a missing header instead of adding it.

Another example is the Cache-Control value in the table. GitHub allows a response to be reused for 60 seconds, so two requests for the same repository a few seconds apart can return the same data even if the repository changed in between. When an agent reports that "the API returns stale data", check the cache headers before you let it change any code.
