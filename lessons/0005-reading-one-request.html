Lesson 5: Reading one request across five systems

About 35 minutes, Module 1 Systems modelAgent craft

When an agent says "the API is down" or proposes a fix for a network error, you need to know which part of the request failed so you can tell whether the fix is aimed at the right part. You don't need to type network commands from memory, because the agent runs them, but you do need to read their output.

A request passes through five systems in order

You have typed URLs into a browser and called fetch() in JavaScript, and in both cases one line of code gave you back a page or some JSON. Behind that line, the request passed through five separate systems, one after another.

The five systems run in a fixed order, and each one has to succeed before the next one starts:

  1. DNS turns the name example.com into an IP address, e.g., 104.20.23.154. The DNS lookup happens before any connection is made.
  2. TCP opens a connection to that IP address on a port, which is 443 for HTTPS. The client and server first exchange three short messages, called the TCP handshake, to agree that the connection is open.
  3. TLS encrypts the connection. In the TLS handshake, the server sends a certificate that proves it owns the name example.com, and both sides agree on encryption keys.
  4. HTTP carries the actual request and response inside the encrypted connection. The client sends a method and a path, e.g., GET /, and the server answers with a status code, e.g., 200, then headers and a body.
  5. The application is the server code that decides what the response says. For your projects, that application is the code you or your agent wrote.

Each system fails with a different kind of error, so the error message tells you which system to look at.

For example, a DNS failure means the name couldn't be found, and no connection was ever attempted. A 404 status means DNS, TCP and TLS all worked, and the server's application answered that it has nothing at that path.

More examples (optional)

A plain http:// URL skips the TLS step, because nothing is encrypted. The request still goes through DNS, TCP and HTTP, but it connects on port 80 instead of 443. The following output was captured on 2026-10-14 with curl -v http://example.com:

*   Trying 172.66.147.243:80...
* Established connection to example.com (172.66.147.243 port 80) ...
* using HTTP/1.x
> GET / HTTP/1.1
> Host: example.com
< HTTP/1.1 200 OK

In the output above, no lines mention TLS, a certificate or a handshake, because the connection isn't encrypted. Anyone on the network path can read and change the request.

A second example is a request your own laptop serves, e.g., http://localhost:3000. In that case, DNS returns the address 127.0.0.1, which is always your own machine, and the request never leaves your laptop. If nothing is listening on port 3000, the TCP step fails, and that failure tells you the server isn't running. It doesn't tell you anything about a bug in your route handler.

Reading curl -v output line by line

An agent that investigates a network problem usually runs curl -v, which makes the request and prints what happens at each of the five steps. The -v flag means verbose, and the output looks dense until you know that the first character of each line says who wrote it.

The curl manual defines the line prefixes as follows (man curl, the --verbose entry):

PrefixMeaning
*A note from curl about what it is doing, e.g., resolving a name, connecting, or checking a certificate
>A header line that curl sent to the server
<A header line that curl received from the server
{ and }Raw data received or sent, shown only as a byte count

The output below is real, and it was captured on 2026-10-14 by running curl -v https://example.com. Some lines are shortened with "...". Each block is coloured by the system it belongs to, and the note beside each block explains it.

* Host example.com:443 was resolved.
* IPv6: 2606:4700:10::ac42:93f3, 2606:4700:10::6814:179a
* IPv4: 104.20.23.154, 172.66.147.243

DNS. curl looked up the name and got two IPv6 and two IPv4 addresses. Large sites return several addresses so that requests spread across many servers.

*   Trying [2606:4700:10::ac42:93f3]:443...
* connect to 2606:4700:10::ac42:93f3 port 443 ...
  failed: Network is unreachable
*   Trying 104.20.23.154:443...

TCP. curl tried the IPv6 address first, but this laptop's network has no IPv6 route, so curl fell back to an IPv4 address. The fallback to IPv4 is normal and isn't an error in the request.

* ALPN: curl offers h2,http/1.1
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
  ...
* TLSv1.3 (OUT), TLS handshake, Finished (20):
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 ...
* ALPN: server accepted h2
* Server certificate:
*   subject: CN=example.com
*   expire date: Dec 25 22:56:35 2026 GMT
*   issuer: C=US; O=SSL Corporation; CN=Cloudflare TLS ...
*   subjectAltName: "example.com" matches cert's "example.com"
* SSL certificate verified via OpenSSL.

TLS. The handshake messages go out (OUT) and come back (IN). The server's certificate names example.com, it hasn't expired, and a trusted issuer signed it, so curl accepts it. ALPN is how the two sides agreed to speak HTTP/2 ("h2").

* using HTTP/2
> GET / HTTP/2
> Host: example.com
> User-Agent: curl/8.21.0
> Accept: */*
>
* Request completely sent off

HTTP request. curl sent the lines on the left. The method is GET, the path is /, and the headers say which site curl wants and what kind of response it accepts. The empty > line ends the headers.

< HTTP/2 200
< content-type: text/html; charset=utf-8
< server: cloudflare
< last-modified: Tue, 13 Oct 2026 20:08:28 GMT
< allow: GET, HEAD

HTTP response from the application. The status 200 means the request succeeded. The headers describe the body, which is HTML here. The server header shows that a Cloudflare server answered, which sits in front of the site's own server.

Curl can also measure how long each system took. The command below prints timings for one request, and every number is the time in seconds from the start of the request (man curl, the --write-out variables). To get the time for one step, you subtract the number before it.

curl -s -o /dev/null -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer}\n' https://example.com
# real output, 2026-10-14:
# dns=0.001209 tcp=0.054150 tls=0.127890 first_byte=0.319773

In the output above, the TLS handshake took 0.128 minus 0.054, which is about 0.074 seconds. The server then took about 0.192 seconds to start sending the response after TLS finished.

More examples (optional)

The same site answered over HTTP/1.1 when curl was told to use that version with --http1.1. In HTTP/1.1, the status line includes a text reason, and header names are often capitalised. Both forms mean the same thing:

< HTTP/1.1 200 OK
< Content-Type: text/html; charset=utf-8
< Connection: keep-alive

A second run of the timing command gave tcp=0.450225 instead of 0.054150. The network is not constant, and one slow TCP connection is normal, so a single timing measurement is weak evidence. Ask the agent to repeat a measurement several times before you trust it.

Finding the part that failed, and checking the agent's fix

When a request fails, curl prints an error with a number, and the message tells you which of the five systems failed. The table below shows real errors captured on 2026-10-14 against test sites that fail on purpose, e.g., badssl.com.

ErrorSystemWhat it means
curl: (6) Could not resolve hostDNSThe name doesn't exist or is misspelled, or DNS is unreachable.
curl: (7) Failed to connect ... Could not connect to serverTCPThe machine was reached, but nothing is listening on that port.
curl: (28) Connection timed outTCPNo answer at all, e.g., a wrong IP address or a firewall that drops packets.
curl: (60) SSL certificate ... has expiredTLSThe server's certificate failed a check, so curl refused to continue.
A status such as 404 or 503HTTP and the applicationThe connection worked, and the server's application answered with an error status.

An agent can make a failing request succeed by switching off the check that failed, so a passing request isn't proof that the agent fixed the problem.

For example, an agent that sees a certificate error may add the -k flag to curl, or set NODE_TLS_REJECT_UNAUTHORIZED=0 in Node. Both settings tell the client to accept any certificate, so the error goes away, but the connection is then open to anyone who can intercept it. The correct fix depends on the cause, e.g., renewing the expired certificate or correcting the host name. You'll find more cases like this in the agent failure catalog.

More examples (optional)

Suppose your Express server is supposed to run on port 3000, and the agent reports curl: (7) Failed to connect to localhost port 3000. If the agent then edits the route handler, it is working on the wrong system. Error 7 is a TCP failure, so the server process isn't running or is listening on another port. The application code never received the request.

Suppose instead the agent reports HTTP 404 from a public API, and it proposes to add retries. A retry repeats the same request, and the server will keep answering that the path doesn't exist. The right next step is to compare the path in the code with the path in the API's documentation.

Do it

  1. Create a practice folder for this module. You'll reuse the folder in later lessons.

    mkdir -p ~/code/agents-lab/module-1   # create the folder, including parent folders
cd ~/code/agents-lab/module-1         # move into it

    You should now see the new path in your terminal prompt, or in the output of pwd.

  2. Run one verbose request and save the output to a file, so you can read it at your own pace.

    curl -v -s -o /dev/null https://example.com 2> trace.txt   # -v output goes to stderr, which 2> saves to trace.txt
less trace.txt                                             # read it; press q to quit

    You should now see lines that start with *, > and <, similar to the annotated output above.

  3. In your own trace.txt, find these three facts and write them down: the IPv4 address that curl connected to, the TLS version, and the HTTP status code.

    You should now have three values, e.g., 104.20.23.154, TLSv1.3 and 200. Yours may differ, because the site has several addresses.

  4. Open your coding agent (Claude Code, Codex, opencode, pi or Amp) in the same folder, and give it this prompt:

    Run curl -v against https://expired.badssl.com and save the output to expired.txt.
Tell me which of these failed: DNS, TCP, TLS, HTTP or the application.
Quote the exact line from the output that proves it.
Don't change any settings to make the request succeed.

    You should now see the agent name TLS and quote a line that mentions an expired certificate. Before you accept the answer, open expired.txt and confirm that the quoted line is really in it.
