Lesson 2: Directing one agent session from plan to proof

About 40 minutes, Module 0 Agent craft

Teams that hire for agent work want developers who get correct, reviewed changes out of an agent, and who don't accept whatever the agent produces. You'll run one complete session, from a written plan to checked proof and a review, which is the routine that every later project in the course uses.

Give each session one task and a design

In lesson 1 you saw that the program sends the whole context to the model on every request, and that unrelated content in the context makes results worse. The first habit follows directly, which is to give each session exactly one task.

Thorsten Ball, who works on the Amp coding agent, writes that "a lot of the problems" new users have can be traced back to "not starting new threads often enough" (How I Use Amp). A thread in Amp is a session, and the Amp documentation says "Use one thread per task" (Amp threads).

The second habit is that you make the design decisions and the agent writes the code. Thorsten Ball describes his prompts this way: "I put in the numbers and the lines and the agent then goes and puts in the colors." He adds that "the agent doesn't make architectural decisions for me".

A directed prompt gives the agent the decisions it shouldn't make on its own. A directed prompt usually covers these parts:

  • the goal, and the files where the change belongs
  • the design, e.g., the function's name, inputs and outputs
  • the edge cases, and the tests to add for each one
  • the limits and the proof, e.g., which files not to touch and what evidence to show at the end
More examples (optional)

A weak prompt leaves the design to the agent:

Add price formatting to the cart.

The agent has to guess the function name, the currency, how to handle zero and bad input, and whether to add tests. Each guess may be reasonable, but you didn't decide any of them, so you can't tell whether the result is what you wanted.

A directed prompt for the same change was tested on 2026-10-14, and you'll use it in the Do it section:

Add a function formatPrice(cents) to cart.js and export it next to total.

Design:
- It takes a whole number of cents and returns a string with a dollar sign
  and two decimals, e.g. formatPrice(1250) returns "$12.50".
- Edge cases: formatPrice(0) returns "$0.00", formatPrice(5) returns "$0.05".
- It throws a RangeError for negative numbers and a TypeError for anything
  that is not an integer.

Tests: add one test for each case above to cart.test.js. Run npm test.
Do not edit package.json or add dependencies.
Proof: paste the full npm test output at the end of your reply.

Ask for proof, and check the proof yourself

An agent's final message often says that the work is done and the tests pass. The final message is model text, and lesson 1 showed that model text is only as reliable as the tool results behind it.

Thorsten Ball asks the agent to "test everything, run through everything end to end", and to give him "irrefutable proof that it works" (How Thorsten uses Amp, updated September 2026). Proof is output that you can check, e.g., the full output of a test run, a command you can run again, or a screenshot of the page.

Your own sense of progress is also weak evidence. In a 2025 study by METR, 16 experienced developers expected AI tools to speed them up by 24%, but they took 19% longer with the tools. After the study, they still believed the tools had sped them up by 20%.

METR has since said that the 2025 numbers are out of date, because the tools improved (METR, February 2026). The gap between what developers felt and what was measured is the part to remember, because it means you should judge an agent's work by evidence.

The agent can only produce proof if it knows how to build and test the project. Thorsten Ball keeps those commands in a file called AGENTS.md: "Since what 'the build' is, is documented in the AGENTS.md, the agent will just run the command and then fix the errors." Lesson 3 covers AGENTS.md in full.

More examples (optional)

The directed prompt above was given to an agent on 2026-10-14, and the agent ended its reply with the test output below. The output is useful proof, because you can run npm test yourself and compare.

✔ total adds price times quantity (0.756973ms)
✔ formatPrice formats cents as dollars (0.140027ms)
✔ formatPrice returns $0.00 for zero (0.119488ms)
✔ formatPrice pads single-digit cents (0.153061ms)
✔ formatPrice throws RangeError for negative numbers (0.317334ms)
✔ formatPrice throws TypeError for non-integers (0.14178ms)
ℹ tests 6
ℹ pass 6
ℹ fail 0

Test output proves that the tests pass, but it doesn't prove that the tests check the right things. A test that asserts nothing also passes. You still read the tests in the diff, which the next section covers, and Module 3 returns to agents that weaken tests.

Use git as the safety net, and review in a fresh session

You already use git to save versions of your work. With an agent, you commit before each session, so that every change the agent makes shows up in git diff and can be thrown away with git restore. Thorsten Ball writes that "the safety net is always version control".

The session that wrote a change is a poor reviewer of it, because its context is full of its own reasoning and assumptions. A new session sees only the code. Thorsten Ball starts a fresh session with a prompt like "Run git diff to see the code someone else wrote. Review it thoroughly and give me a report".

You then decide which findings are correct, because a reviewing agent can be wrong too. Small cleanup, e.g., removing debug statements, also goes in its own new session, and Thorsten Ball does the same.

More examples (optional)

Suppose the review session reports that formatPrice(1.5) should throw a TypeError but no test checks it. You can confirm the finding by reading the test file. If it is correct, you give the fix to a new session with one directed sentence, and you check the new test output.

Suppose instead the review session says that the function should accept strings like "1250". Your design said it takes a whole number of cents, so the finding is wrong for your design, and you ignore it.

Read more: git restore documentation

Do it

  1. Go to the tiny-shop project from lesson 1, and commit it as the starting point.

    cd ~/code/agents-lab/module-0/tiny-shop        # the project from lesson 1
git init -b main                                # start a repository on a branch called main
git add .                                       # stage all three files
git commit -m "Add tiny-shop starting point"    # save the starting point

    You should now see a line that ends with Add tiny-shop starting point, followed by 3 files changed, 15 insertions(+).

  2. Write a directed prompt for this task: add a function formatPrice(cents) to cart.js that returns a price string such as "$12.50". Use the four parts from the list above, and choose the edge cases yourself before you look at the example in the first section.

    You should now have a prompt that names the function, lists at least three edge cases, asks for a test for each one, and says what proof to show.

  3. Start a new agent session in the tiny-shop folder, and give it your prompt.

    You should now see the agent edit cart.js and cart.test.js, run npm test, and end with the test output.

  4. Check the proof yourself, in your own terminal.

    npm test                # run the tests yourself
git diff --stat         # list which files changed and by how much

    You should now see the same number of passing tests that the agent reported, and only cart.js and cart.test.js in the list of changed files.

  5. Start another new session, and ask it to review the change.

    Run git diff to see the code someone else wrote.
Review it thoroughly and give me a report.
Don't change any files.

    You should now see a report. For each finding, write down whether it is correct for your design.

  6. Keep the change, or throw it away. Before you throw anything away, run git status and read the list, because git restore deletes uncommitted changes and you can't get them back.

    git status                                         # check which files would be affected

    To keep the change, commit it:

    git commit -am "Add formatPrice for cart display"  # keep the change

    To throw the change away instead, run only this command:

    git restore .                                      # discard all uncommitted changes

    You should now see a clean working tree when you run git status again.
