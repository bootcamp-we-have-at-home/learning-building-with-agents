Lesson 8: Deciding whether to build, buy or self-host, starting with fetch

About 40 minutes, Module 1 Build, then buyAgent craft

An agent will add a library or a service whenever you ask for a feature, so you need to decide on purpose which code your project owns and which code it borrows. Employers ask junior developers to explain those choices in reviews and interviews, and a written decision record gives you that explanation.

Libraries and services change what you need to build yourself

In lesson 5 you read a request made with curl, and in your own code you have made the same kind of request with fetch(). Whenever your app needs a feature such as an HTTP client, a login system or a styling system, you have the same set of choices.

The choices differ in who writes the code, who runs it, and where the data lives:

  1. Build means you write the code, and you test and maintain it yourself.
  2. Library means you install someone else's code into your app from npm, and it runs inside your app.
  3. Self-hosted service means you install and run a separate program on your own server, and your app talks to it over HTTP.
  4. Hosted service means a company runs the program on its servers, and your app sends requests to it. You pay with money, or with a free tier that has limits.

Login is the clearest example, and Module 4 covers it in depth. Each option below was checked on 2026-10-14.

You can only judge a library if you know what it does for you, so the rule in this course is to build a small version once and then decide whether to buy.

Building the small version shows you which parts are easy and which parts are hard. For example, a hand-written login teaches you that storing a password safely and expiring a session are the hard parts, so you know to check that better-auth handles them before you trust it.

More examples (optional)

Styling has the same choices. You can write your own CSS and theme variables, or you can use a library such as Tailwind CSS or Meta's StyleX. The npm download counts for the week of 2026-10-06 to 2026-10-12 were 137,279,787 for tailwindcss and 2,126,860 for @stylexjs/stylex. Both are MIT licensed and both had releases in 2026.

For a junior job search, the download gap is the deciding signal, because job adverts and existing codebases use Tailwind far more often. StyleX is worth reading about as a comparison, since it compiles styles at build time, but you would learn Tailwind first.

A second example is a weather widget that shows today's temperature. A hosted weather API is the only sensible choice, because you can't build or run your own weather stations, so the decision is only about which provider to use.

Read more: better-auth, Keycloak, and StyleX as an optional comparison with Tailwind

Building the small version of fetch once

The built-in fetch() function has a behaviour that surprises most developers. MDN's guide Using the Fetch API says that fetch() rejects "on some errors, but not if the server responds with an error status like 404".

In other words, a 404 or a 500 from lesson 6 doesn't throw, so code that forgets to check response.ok carries on as if the request worked. By default, fetch() also waits as long as the network allows, with no timeout.

A small wrapper fixes both problems. The function below is about the size of the toy you'll ask an agent to build:

async function getJson(url, { timeoutMs = 5000 } = {}) {
  const res = await fetch(url, { signal: AbortSignal.timeout(timeoutMs) }); // give up after timeoutMs
  if (!res.ok) throw new Error(`HTTP ${res.status} for ${url}`);            // turn 4xx and 5xx into errors
  return res.json();                                                         // parse the body as JSON
}

The output below is real, and it was captured on 2026-10-14 with Node v26.7.0. It compares plain fetch(), the wrapper, and the ky library that you studied in lesson 4:

plain fetch: 404 ok = false
wrapper: HTTP 404 for https://httpbin.org/status/404
wrapper timeout: TimeoutError
ky: HTTPError Request failed with status code 404: GET https://httpbin.org/status/404
ky timeout: TimeoutError

Plain fetch() returned the 404 without an error, while the wrapper and ky both threw. Ky does more than the toy, and its README lists retries, hooks, a base URL option and upload progress. By default, ky retries GET requests twice on statuses such as 429 and 503, and it uses a 10-second timeout.

More examples (optional)

Ky's default retry list doesn't include 404. A 404 means the path doesn't exist, so a retry would get the same answer, which is the same reasoning as in lesson 5.

Ky also doesn't retry POST requests by default. A POST isn't idempotent, as lesson 6 explained, so sending it twice could create two orders. If an agent turns on retries for POST, ask it how the server prevents duplicates.

The wrapper and ky each have a cost. The wrapper is about five lines that you test and maintain yourself. Ky is about 600 KB unpacked on npm and has no dependencies, but you depend on its maintainers for fixes and for changes between major versions.

Read more: ky README, "Benefits over plain fetch", and MDN, AbortSignal.timeout()

A single number can mislead you. For example, on 2026-10-14 ky had 0 open issues and 453 closed ones, which shows that its maintainers resolve or close every report, and it doesn't show that ky has no bugs. Download counts also include automated builds, so they measure how much code depends on a package and not how many people like it.

You write the result in a decision record, which is a short Markdown file in the repo that says what you chose and why. The decision record template follows Michael Nygard's 2011 format, and lesson 3 explained why the reason has to live in the repo where the next agent session can read it.

Do it

  1. Create a folder for the comparison inside the module folder from lesson 5, and set up an npm project in it.

    mkdir -p ~/code/agents-lab/module-1/http-client   # new folder for this lesson
cd ~/code/agents-lab/module-1/http-client         # move into it
npm init -y                                        # create package.json with defaults
git init                                           # start a repo so you can review diffs

    You should now see a package.json file when you run ls.

  2. Open your coding agent in the folder and ask it to build the toy version. The prompt names the behaviour and the proof, as lesson 2 taught.

    Create compare.mjs with a function getJson(url, { timeoutMs }) that uses plain fetch,
throws on any non-2xx status, aborts after timeoutMs with AbortSignal.timeout,
and returns the parsed JSON. Don't install any packages.
Then call it on https://httpbin.org/status/404, on https://httpbin.org/delay/3
with timeoutMs 1000, and on https://httpbin.org/json, and print what happens.
Run it with node and show me the output.

    You should now see output similar to the captured output above, with an HTTP 404 error, a TimeoutError, and the keys of the JSON body.

  3. Commit the toy, then ask the agent to write the same three calls with ky in a second file.

    git add -A && git commit -m "Add getJson toy fetch wrapper"   # save the toy before the agent changes anything

    Then give the agent this prompt: "Install ky, write ky.mjs that makes the same three calls with ky, run both files, and show both outputs side by side." You should now see ky throw an HTTPError for the 404 and a TimeoutError for the slow call.

  4. Ask the agent to collect the dependency signals for ky and print them as a table.

    Collect these for the npm package ky and print a table: weekly downloads from
https://api.npmjs.org/downloads/point/last-week/ky, latest version and its release date
from npm view, licence, unpacked size, number of dependencies, and open issues from
the GitHub API. Include the date you collected them.

    You should now see a table similar to the one above, with today's numbers.

  5. Write docs/decisions/0001-http-client.md yourself, using the template, and choose between the wrapper and ky for the Module 1 project. Write the record without the agent, because the decision is yours.

    You should now have a record with all five sections and a date next to every number.

Check yourself

Decide which option fits each situation. Recall the four options from memory first, without scrolling up.

One page needs to wait 300 ms after the user stops typing before it searches.

A weekend demo needs a login for about 200 users, and nobody on the team can run servers.

An app must keep user accounts in the company's existing PostgreSQL database, and there's no operations team.

A company has twelve internal apps that need one shared login, identity data must stay on its own servers, and it has an operations team.

A large app makes hundreds of API calls, and it needs retries on 429 and 503, timeouts and shared headers.
